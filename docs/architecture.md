# Architecture

## Why static translation

An emulator decodes and interprets each 68000 instruction at run time. This project instead
runs the game's own algorithms as C:

1. `tools/core/m68000/analysis.py` finds code reachable from the exception vectors and
   `symbols.txt`, following direct and computed branches, jumps and calls, and the handler
   tables those reach.
2. `tools/core/m68000/translate.py` lifts every instruction to an IR and writes one C function
   per game function. The C manipulates the 68000 register file and calls the board through the
   bus helpers.
3. The generated C is compiled with this project's board runtime. No instruction fetch, decode,
   or 68000 interpreter remains in the shipped binary.

The board runtime is the only emulation-like layer: it models the memory-mapped registers, video
chips, inputs and sound chip behaviour. That is the hardware the arcade board ran on, not a CPU
emulator.

## Layers

### Generated program (`build/generated/`)

- `program.h`: prototypes plus `PROGRAM_FRAME_WAIT`.
- `program_NN.c`: the translated functions.
- `entries.c`: `m68k_code_entries[]`, the address-to-function table used by computed jumps,
  interrupts and the reset vector.

Generated output is derived from the user's ROM and is git-ignored. It is never distributed.

### 68000 runtime (`runtime/src/m68000.c`)

Provides the contract the generated C expects:

- `m68k_cpu cpu` with D0-D7, A0-A7, the other stack pointer, the system byte and X/N/Z/V/C.
- `m68k_read_sr` / `m68k_write_sr`, including the supervisor/user stack swap.
- `m68k_call`, `m68k_jump`, `m68k_calls_push`, `m68k_returned_to`.
- `m68k_exception`, `m68k_take_interrupts`, `m68k_stop`, `m68k_reset_devices`.
- `program_frame_wait`, called at the game's idle instruction (`0x04F382`), which advances the
  board to the next VBLANK and lets pending interrupts run.

Bus semantics follow MAME's 68000 core: a long is its high word then its low one; a byte is
written on both halves of the bus with a `mem_mask` (`0xFF00` even, `0x00FF` odd).

### Board (`runtime/src/machine.c`)

`cave_machine` owns:

- the 1 MiB program ROM supplied by the player at run time;
- 64 KiB work RAM;
- 64 KiB sprite RAM;
- layer 0/1/2 tile RAM at `0x500000`, `0x600000`, `0x700000`;
- 64 KiB palette (`0x8000` xGRB_555 entries);
- 128 bytes of video registers and the IRQ-cause latch;
- three layer control register banks;
- inputs, EEPROM state and coin counters;
- the YMZ280B register file and sample ROM.

Addresses outside a device are counted as bad accesses; the headless runner fails on them.
The 24-bit address bus is masked, matching the 68000's address lines.

### Video (`runtime/src/video.c`)

The visible resolution is 320x240, rotated 270 degrees for the cabinet. Three 038-style tile
layers (8x8 and 16x16 tiles, row scroll/row select) and the NEC 013 sprite generator are drawn
in priority order. The renderer is being implemented; the current build draws only the
background colour.

### Audio (`runtime/src/ymz280b.c`)

The YMZ280B is implemented from its register interface: key-on/off, sample start/end addresses,
pitch, level, pan, loop and ADPCM decoding, with the 4 MiB sample ROM supplied by the player.
The register interface is present; the mixer is the audio milestone.

### Ports (`ports/headless`, `ports/sdl2`)

- Headless: deterministic frame loop, per-frame hashes, exit code on a missing translated entry
  or an invalid bus access. This is the CI gate.
- SDL2: window, texture, input mapping, audio device and frame pacing; same
  `program_reset` / `program_run` entry points as headless.

## Boot and frame model

The board boots at the 68000 reset vector: SSP `0x110000`, PC `0x00595A`. The reset routine
initialises hardware, runs the ROM checksum, and reaches the main loop. The frame-wait routine
is `0x04F35E`; its idle instruction is `0x04F382` (`tst.w $100F04`). The level-1 VBLANK handler
at `0x00061A` sets `$100F04` at `0x000646`.

Translated instructions take no time. `program_frame_wait()` is called at `0x04F382`; it advances
the board one frame, raises VBLANK (level 1) and refreshes video. `m68k_take_interrupts()` then
runs the handler. This mirrors MAME's frame timing.

## Determinism

The game's random numbers are generated by its own code from RAM state; no host RNG is used.
Headless runs are reproducible for a fixed ROM, input script and frame count.

## Security and distribution

The executable opens the user's ZIP, verifies every file by CRC32 and SHA-1, extracts only known
region names, and loads program/sample/graphics regions into private buffers. It does not execute
data from the ZIP and ships no ROM bytes. Release archives contain only binaries, licenses and
documentation.
